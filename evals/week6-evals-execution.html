01 · BEFORE THE LOOP

What runs before question 1

python -m evals.run --repeat 3 starts in main(). Before any question is asked, two things happen in order.

argparse — reads --label, --repeat, --compare
index_directory() — same indexer app.py and the CLI use
if args.compare: compare(*args.compare) # diffs two saved runs, never calls the model return indexed = index_directory(get_settings().articles_dir) if indexed: print(f"Checked {len(indexed)} document(s); only new content was embedded.")

The index step is idempotent, not a fresh rebuild. index_directory() re-reads all 5 menu files every run, but index_text() (from Week 1–3's rag_chat/ingestion.py) hashes each chunk's content into its Chroma id and skips any id already stored — so re-running the eval suite back to back costs one cheap existence check per chunk, not 5 documents' worth of re-embedding.

02 · EXECUTION ORDER

The trace — what happens for each of the 25 questions

Six stations per test case, always in this order, printed as [n/25] <question> as it goes. With --repeat 3, stations 03–04 run three full times per case before station 05 ever sees a result.

01
main() → for case in TEST_CASES

One test case at a time, in file order

evals/testset.py holds 25 TestCase entries — the same 25 questions from Week 5's error analysis. Each one carries the question text, which documents it should retrieve, a reference ground_truth, whether it should refuse, and — for the 8 that failed last week — which named failure group (A–E) it belongs to.

02
run_case(case, repeat=N)

Run the same question N times, independently

Chat-model answers vary run to run — a single pass can make a fix look better or worse than it really is by luck. So run_case() calls run_one_trial(case) repeat times (each one a full, independent live call — nothing is cached between trials), then scores the case by majority vote.

def run_case(case, repeat=1): trials = [run_one_trial(case) for _ in range(repeat)] pass_rate = sum(1 for t in trials if t["passed"]) / len(trials) majority = pass_rate >= 0.5
03
run_one_trial() → retrieve(question)

Find the chunks, then label them by source

This is the full Week 3–5 retrieval stack, unchanged: hybrid search (semantic + BM25) fused with reciprocal rank fusion, then a wider candidate window judged by an LLM reranker (Week 4) against the exact question. What's new this week is the last step — each surviving chunk is now returned prefixed with [Source: filename], instead of raw unlabeled text.

labeled_chunks = [ f"[Source: {metadata_by_id[cid]['source']}]\n{text_by_id[cid]}" for cid in chunk_ids if cid in text_by_id ] return labeled_chunks, sources

Without this label, a chunk from deep in a menu file (past the point where the restaurant's name is stated) gave the model no way to tell two shops' "Filter Coffee" lines apart — the root cause behind Week 5's biggest failure group.

04
run_one_trial() → generate_response(question, chunks)

Answer, told explicitly which passage is whose

The labeled chunks are joined into one context block. The system prompt sent alongside it (Week 6's one change) tells the model to match the question's named entity to a [Source: ...] label, answer only from the matching passage(s), address multiple entities separately instead of blending them, and never echo the raw label back in its answer.

05
run_one_trial() → score the answer

Free checks first, then the judge — but only sometimes

check_sources() and check_refusal_behavior() run first (evals/checks.py, no API call). What happens next branches on one field of the test case:

should_refuse = True

The rule check already answers the only question that matters — did it refuse? Grading a refusal against a reference sentence adds nothing, so judge_answer() is skipped entirely. passed = source_check and refusal_check.

should_refuse = False

judge_answer() is called: one more LLM call, grading the answer against ground_truth with a binary CORRECT/INCORRECT verdict. An unparsable judge reply fails closed to INCORRECT, never silently skipped. passed requires all three checks to agree.

06
run_case() → back from the inner loop

Vote, then keep one representative trial

Once all repeat trials are in, run_case() takes the majority verdict and keeps one matching trial's full detail (sources, answer text, judge reason) to report — plus the raw pass_rate, so a 2-of-3 split is visible instead of hidden behind a single true/false.

After all 25 cases: print_report(results) prints an overall score, a per-group table (A–E plus "previously passing"), and full detail for every case that failed — then save_results() writes the whole list to evals/results/<label>.json via dataclasses.asdict(), ready to be diffed later.

03 · THE OTHER PATH

--compare takes a completely different branch

Back at station 01: if --compare before after is passed, none of the stations above ever run. compare() loads two previously-saved evals/results/*.json files, recomputes each group's pass count from the stored data, and prints a table plus two id lists — no retrieval, no generation, no judge, no cost.
